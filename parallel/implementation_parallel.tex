\begin{abstract}
本文档描述 dynamic private proof-of-assets 原型系统的本地实验代码架构。目标是在真实 Ethereum block delta 上实现并测试两条路线：一是 algebraic fixed-set NIZK update，包括 masked KZG set commitment、batched KZG evaluation、structured $C_Y$ opening、committed-R1CS/Bulletproof logic proof，以及按 shard 并行构造多个小多项式的实现路径；二是 compact SMT-SP1 update，包括 salted sparse Merkle tree、membership/non-membership witness、conditional update program、address insertion program，以及初始化阶段的 Ethereum Merkle/MPT proof verification program。SMT 方案不再使用手写 Halo2 circuit，而是使用 SP1 zkVM 加协处理器/预编译加速路径来证明 Rust 程序的正确执行。本文明确代码目录、每个文件的功能、核心算法、环境配置、依赖库、输入输出格式和 benchmark 命令。
\end{abstract}

\section{Implementation Scope}

实验原型只测试 proof-of-assets 的 asset side。初始化阶段从 Ethereum 读取一批 sample addresses 的 native ETH balances，但不运行真实私钥持有证明，因为实验者并不持有这些地址的私钥。论文实验中应明确说明：ownership proof 被替换为 dummy predicate，benchmark 只测 state binding、commitment construction、update proving、verification 和 insertion proving 的成本。

主实验支持三类操作：
\begin{enumerate}[leftmargin=2em]
  \item \textbf{Initialization}: 给定 reserve address set $S$ 和起始 block $b_0$，读取 $\bal_{b_0}(a)$，构造初始 public state。
  \item \textbf{Dynamic update}: 给定 block window $[b_{i-1},b_i]$ 的 canonical delta list $\Delta_i$，证明 aggregate balance commitment 被正确更新。
  \item \textbf{Insertion}: 给定新地址集合 $S_{\mathsf{new}}$，测试 SMT insertion proof；NIZK route 只测试 reinitialization 和 polynomial-maintenance cost。
\end{enumerate}

主实验暂时只考虑 account-based chain 上的一种 fungible asset，即 Ethereum native ETH balance。ERC-20、多资产和多链聚合放在扩展实验中。

The synchronizer is a deterministic public program:
\[
  \Delta_i=\Sync(b_{i-1},b_i).
\]
It returns a sorted, deduplicated list
\[
  \Delta_i=((a_1,\delta_1),\ldots,(a_m,\delta_m)),
\]
where $\delta_j=\bal_{b_i}(a_j)-\bal_{b_{i-1}}(a_j)$ and zero deltas are removed.

For the algebraic NIZK route, KZG is implemented directly over arkworks powers-of-$\tau$ SRS rather than treated as a black-box polynomial-commitment crate. This is necessary because the protocol needs explicit access to structured bases
\[
  B_j=[L_j(\tau)]_1,\qquad H_Y=[Z_i(\tau)]_1.
\]
The committed-R1CS/Bulletproof logic layer is implemented in a separate crate over the same $\G_1$ group as the KZG source group. If the first engineering prototype cannot finish the full Bulletproof backend, it should still output exact R1CS size and benchmark KZG/evaluation components separately; the final paper experiment should clearly distinguish exact implementation from estimated logic-layer cost. The SMT route is implemented by ordinary Rust programs compiled to SP1 RISC-V ELF files. Expensive cryptographic subroutines such as Keccak/MPT node hashing and batched SMT path hashing are routed through the SP1 coprocessor/precompile abstraction whenever possible.

Synchronizer algorithm:
\begin{enumerate}[leftmargin=2em]
  \item Fetch modified accounts between \texttt{start\_block} and \texttt{end\_block}.
  \item For each address $a$, fetch $b_{\mathsf{old}}=\bal_{b_{i-1}}(a)$ and $b_{\mathsf{new}}=\bal_{b_i}(a)$.
  \item Set $\delta=b_{\mathsf{new}}-b_{\mathsf{old}}$.
  \item Remove entries with $\delta=0$.
  \item Sort by address bytes and merge duplicates by summing deltas.
  \item Output \texttt{DeltaWindow} with both block hashes and state roots.
\end{enumerate}

\subsubsection{Efficient initialization for the fixed-set NIZK route}

The fixed-set NIZK route also needs a real initialization proof, not only local construction of
$P_S$, $A$ and $C_0$.  A direct circuit that verifies all Ethereum account proofs, multiplies the
whole set polynomial, and recomputes the KZG MSM inside one monolithic proof is possible, but it is
not the preferred implementation.  The prototype uses a split initialization proof
\[
  \pi_{\mathsf{init}}=(\pi_{\mathsf{chain}},\pi_{\mathsf{alg}})
\]
with a common hidden-list digest $D_{\mathsf{init}}$.  This keeps Keccak/RLP-heavy chain-state
verification inside SP1, while keeping the algebraic KZG and aggregate-commitment checks inside the
same committed-R1CS/Bulletproof layer as the update protocol.

\paragraph{Private initialization list.}
The prover starts from a private ordered list
\[
  L=((a_1,b_1,\pi^{\mathsf{acct}}_1,\omega^{\mathsf{own}}_1),\ldots,
     (a_n,b_n,\pi^{\mathsf{acct}}_n,\omega^{\mathsf{own}}_n)),
\]
where $a_k$ is an Ethereum address, $b_k$ is the claimed balance under the finalized state root
$\sr_0$, $\pi^{\mathsf{acct}}_k$ is the Ethereum account proof, and $\omega^{\mathsf{own}}_k$ is an
ownership proof.  In the local experiment, $\omega^{\mathsf{own}}_k$ is replaced by a dummy predicate
because the benchmark addresses are sampled from Ethereum and the experimenter does not hold their
private keys.  The real protocol should instantiate $\omega^{\mathsf{own}}_k$ as a signature on a
domain-separated initialization challenge, for example
\[
  \mathsf{ch}=\Hash(\mathtt{poa\mbox{-}init},\sr_0,A,C_0,\mathsf{srs\_hash},\mathsf{session\_id}).
\]
For an EOA-only prototype this is ordinary secp256k1 signature verification; contract wallets can be
added later as a separate ownership predicate.

To bind the two initialization subproofs to the same private list without revealing the addresses,
the prover samples a long random salt $\nu$ and computes
\[
  D_{\mathsf{init}}=\Hash(\mathtt{init\mbox{-}list},\nu,n,
      (\Enc(a_1),b_1),\ldots,(\Enc(a_n),b_n)).
\]
The digest is public and both subproofs recompute it.  The salt prevents offline dictionary tests
against candidate reserve sets, while collision resistance gives binding to one ordered list.

\paragraph{SP1 chain-state subproof.}
The SP1 guest program \texttt{nizk-init-chain} takes as private input the account-proof objects and
ownership witnesses, and as public input $(\sr_0,D_{\mathsf{init}},n)$.  It performs the following
checks.
\begin{enumerate}[leftmargin=2em]
  \item Decode each account proof and verify the Ethereum Merkle-Patricia-Trie path from
        $\Hash(a_k)$ to the public state root $\sr_0$.
  \item Decode the account object and check that its balance equals $b_k$.
  \item Verify the ownership predicate $\omega^{\mathsf{own}}_k$, or the dummy predicate in
        benchmark mode.
  \item Recompute $D_{\mathsf{init}}$ from $(\nu,n,(\Enc(a_k),b_k)_k)$.
  \item Check balance range bounds and reject malformed encodings.
\end{enumerate}
The host code first runs the same verifier natively to catch bad RPC data, then runs SP1 mock
execution, and finally produces the real proof only for benchmark runs.

\paragraph{Algebraic subproof.}
The host constructs
\[
  F_S(T)=\prod_{k=1}^{n}(T-x_k),\qquad x_k=\Enc(a_k),\qquad
  P_S(T)=\alpha F_S(T),
\]
where $\alpha\leftarrow\F_q^*$, and computes
\[
  A=[P_S(\tau)]_1,
  \qquad
  B_0=\sum_{k=1}^{n} b_k,
  \qquad
  C_0=B_0V+r_0H_B.
\]
The coefficients of $P_S(T)=\sum_{t=0}^{n}p_tT^t$ are private witnesses.  The algebraic proof
$\pi_{\mathsf{alg}}$ is a committed-R1CS/Bulletproof proof with external group-linear equations
\[
  A=\sum_{t=0}^{n}p_t[\tau^t]_1,
  \qquad
  C_0=B_0V+r_0H_B.
\]
Thus the proof does not implement BLS12-381 group arithmetic or pairings inside the R1CS: the group
relations are verified by the Bulletproof opening layer against public bases.  The field constraints
only prove that the hidden coefficients define the right set polynomial and the right aggregate
balance.

The efficient trick is to avoid proving the full coefficient identity
$P_S(T)=\alpha\prod_k(T-x_k)$ by polynomial multiplication constraints.  After $A,C_0$ and
$D_{\mathsf{init}}$ are fixed, the verifier derives a Fiat-Shamir challenge
\[
  \zeta=\Hash_{\F}(\mathtt{init\mbox{-}poly\mbox{-}check},\sr_0,A,C_0,D_{\mathsf{init}},n).
\]
The proof checks the single random evaluation identity
\[
  \sum_{t=0}^{n}p_t\zeta^t
  =
  \alpha\prod_{k=1}^{n}(\zeta-x_k),
  \qquad \alpha\ne 0.
\]
The left side is computed by Horner evaluation in $O(n)$ field operations; the right side is a
running product in $O(n)$ multiplication gates.  Since $A$ binds to a unique degree-at-most-$n$
polynomial under KZG binding, a wrong polynomial passes this random evaluation check with probability
at most $n/q$ in the random-oracle model.  This replaces an expensive in-circuit product-tree proof
with a linear-size probabilistic product argument.

The same proof also checks
\[
  B_0=\sum_{k=1}^{n} b_k,
  \qquad
  D_{\mathsf{init}}=\Hash(\mathtt{init\mbox{-}list},\nu,n,(x_k,b_k)_k),
\]
and all integer range constraints needed for the chosen balance encoding.  If full duplicate
prevention is required inside the proof, add one of the following checks:
\begin{enumerate}[leftmargin=2em]
  \item a private sortedness-and-adjacent-inequality proof over address limbs; or
  \item a private SMT insertion proof that inserts every $x_k$ into an initially empty local tree and
        checks non-membership before each insertion.
\end{enumerate}
For the first prototype, duplicates should also be rejected in the native preprocessing pipeline; the
formal benchmark can report the extra cost of the duplicate-prevention gadget separately.

\paragraph{Verifier.}
The verifier accepts the initial state
\[
  X_0=(\sr_0,A,C_0)
\]
only if both subproofs verify for the same public tuple
$(\sr_0,A,C_0,D_{\mathsf{init}},n,\mathsf{srs\_hash})$.  The public output stored in
\texttt{outputs/states/nizk\_init.json} should include $\sr_0$, block hash, $A$, $C_0$, proof hashes,
SRS hash, $n$, balance encoding bounds and benchmark metadata.  The private state stored locally
contains $S$, $\alpha$, the polynomial coefficients of $P_S$, $B_0$, $r_0$, and the account-proof
cache used for reproducibility.

\paragraph{Complexity.}
Let $n=|S|$.  Native polynomial construction costs $\widetilde O(n)$ field operations with a product
tree, and the KZG commitment costs one MSM of length $n+1$.  The algebraic initialization proof uses
$O(n)$ field constraints for Horner evaluation, the product check, the balance sum and the external
commitment openings, plus the cost of the digest and optional duplicate-prevention gadget.  The SP1
chain subproof costs $O(n)$ Ethereum account-proof verifications; its dominant costs are RLP parsing,
Keccak/MPT hashing and ownership signature verification.  This is still a one-time cost, while later
updates use the much cheaper multipoint-evaluation and committed-R1CS update protocol.

Update algorithm:
\begin{enumerate}[leftmargin=2em]
  \item Encode query points $x_j=\Enc(a_j)$ and check distinctness.
  \item Compute $y_j=P_S(x_j)$ by fast multipoint evaluation.
  \item Set $u_j=1$ iff $y_j=0$ and compute $d=\sum_j u_j\delta_j$.
  \item Build $Z_i(T)=\prod_j(T-x_j)$ and interpolate $I_y(T)$.
  \item Sample $\rho_Y$ and compute $J_Y=I_y+\rho_YZ_i$.
  \item Commit $C_Y=[J_Y(\tau)]_1$ and prove $P_S-J_Y$ is divisible by $Z_i$.
  \item Commit $C_U=\sum_j u_jU_j+r_UH_U$ and $C_D=dV+r_DH_B$.
  \item Prove the committed-R1CS relation for bitness, zero-test and $d=\sum_j u_j\delta_j$.
  \item Output $C_i=C_{i-1}+C_D$ and proof object.
\end{enumerate}


\subsubsection{Parallel sharded implementation for the fixed-set NIZK route}\label{sec:impl-parallel-nizk}

For large reserve sets, the prototype should support a sharded mode in which the single polynomial
$P_S$ is replaced by $t$ smaller masked set polynomials.  The purpose is to reduce wall-clock prover
time and memory pressure during initialization, multipoint evaluation and quotient computation.
The public state stores the vector of shard commitments
\[
  A=(A_1,\ldots,A_t),
  \qquad
  A_\ell=[P_\ell(\tau)]_1,
  \qquad
  P_\ell(T)=\alpha_\ell\prod_{a\in S^{(\ell)}}(T-\Enc(a)).
\]
The values $t$ and the public shard-size bounds are recorded in the transcript and in the output JSON.
For experiments that should not reveal the exact shard distribution, use balanced padding so that all
shards have the same public size bound.

\paragraph{Configuration.}
Add the following configuration block to \texttt{configs/bench-nizk.toml}:
\begin{lstlisting}
[nizk.sharding]
enabled = true
shards = 8                 # or "auto" from physical cores
size_policy = "balanced-pad"
batch_kzg = true
aggregate_inner_product = true
rayon_threads = 8
\end{lstlisting}
The command-line interface should expose the same parameters:
\begin{lstlisting}
poa nizk init   --shards 8 --size-policy balanced-pad --mode full
poa nizk update --shards 8 --batch-kzg --aggregate-ip
\end{lstlisting}

\paragraph{Data structures.}
The sharded code should use explicit serializable structs rather than implicit arrays:
\begin{lstlisting}
struct ShardState {
    shard_id: usize,
    size_bound: usize,
    alpha: Fr,
    coeffs: Vec<Fr>,      // coefficients of P_l
    commitment: G1Affine, // A_l
}

struct ShardUpdateProof {
    shard_id: usize,
    c_y: G1Affine,
    pi_eval: G1Affine,
    c_u: G1Affine,
    zero_test_proof: Bytes,
    component_ms: ShardTimings,
}

struct ParallelUpdateProof {
    shard_proofs: Vec<ShardUpdateProof>,
    c_u_sum: G1Affine,
    c_d: G1Affine,
    projection_proof: Bytes,
    batch_kzg_randomizers: Vec<Fr>,
}
\end{lstlisting}
Only the benchmark/debug build should serialize plaintext shard witnesses such as the local
$u^{(\ell)}$ vectors.  The proof output should serialize commitments, proofs and timing metadata.

\paragraph{Parallel initialization pipeline.}
Initialization proceeds as follows.
\begin{enumerate}[leftmargin=2em]
  \item Load the private reserve list, verify/sort it in native preprocessing, and split it into
        $t$ balanced shards.  The formal proof must still prove duplicate-freeness globally, not only
        inside each shard.
  \item Run the SP1 account-proof/ownership subproof either once over the whole list or in chunks.
        When it is chunked, every chunk proof must bind the same salted initialization digest or a
        Merkle root of the private ordered list.
  \item Use \texttt{rayon::par\_iter} over shards.  Worker $\ell$ constructs $P_\ell$, samples
        $\alpha_\ell$, computes $A_\ell$, and generates the shard algebraic product proof.
  \item The coordinator sums balances once to form $B_0$ and $C_0$, collects
        $(A_\ell)_\ell$, and writes the initial state
        \texttt{outputs/states/nizk\_init\_parallel.json}.
\end{enumerate}
The implementation should report both total CPU time and wall-clock time.  This distinction matters
because the total polynomial work can increase slightly from repeated per-shard interpolation, while
wall-clock time should decrease when the degree-$n$ operations dominate.

\paragraph{Parallel update pipeline.}
For every epoch, the host computes the public query points and the query vanishing polynomial once:
\[
  x_j=\Enc(a_j),\qquad Z_i(T)=\prod_j(T-x_j).
\]
Then it runs the following parallel worker routine for each shard:
\begin{enumerate}[leftmargin=2em]
  \item evaluate $P_\ell$ at all $x_j$;
  \item compute $u_j^{(\ell)}=1[P_\ell(x_j)=0]$;
  \item build $J_\ell=\sum_j y_j^{(\ell)}L_j+\rho_{Y,\ell}Z_i$;
  \item output $C_{Y,\ell}$ and $\pi_{\mathsf{eval},\ell}$;
  \item commit $C_{U,\ell}=\sum_j u_j^{(\ell)}U_j+r_{U,\ell}H_U$ and prove the local zero-test
        relation linking $C_{U,\ell}$ and $C_{Y,\ell}$.
\end{enumerate}
The coordinator then computes the aggregate status vector and commitment
\[
  u_j=\sum_{\ell=1}^{t}u_j^{(\ell)},
  \qquad
  C_U=\sum_{\ell=1}^{t}C_{U,\ell},
\]
and creates exactly one projection proof for
\[
  d=\sum_j u_j\delta_j,
  \qquad
  C_D=dV+r_DH_B,
  \qquad
  C_i=C_{i-1}+C_D.
\]
Thus the expensive balance inner product is not proved once per shard.  It is proved once after the
shard-local membership vectors have been summed.  In the first implementation, workers are internal
threads and may pass plaintext witnesses to the coordinator.  A later distributed-prover version can
replace this by an MPC-style summation of committed vectors, but that is not necessary for the local
benchmark.

\paragraph{Batch KZG verification.}
Because all shard proofs use the same $Z_i$, the verifier should not run $t$ independent pairing
checks.  After hashing the full transcript, it derives $\beta_1,\ldots,\beta_t$ and checks
\[
  e\!\left(\sum_{\ell=1}^{t}\beta_\ell(A_\ell-C_{Y,\ell}),[1]_2\right)
  =
  e\!\left(\sum_{\ell=1}^{t}\beta_\ell\pi_{\mathsf{eval},\ell},[Z_i(\tau)]_2\right).
\]
The implementation should still keep a debug flag that verifies every shard separately, because this
makes it easier to locate a faulty worker during development.

\paragraph{Benchmark fields.}
The NIZK benchmark JSON should include sharding-specific fields:
\begin{lstlisting}

  "m": 4096,
  "shards": 8,

  "batch_kzg_verify_ms": 4.3,

\end{lstlisting}

\paragraph{Initialization program.}
The SP1 program \texttt{init-merkle} takes as public input the Ethereum state root $\sr_0$, the claimed local SMT root $R_0$, the claimed balance commitment $C_0$, the reserve-set size $n$, and parameter hashes. Its private input contains addresses, balances, salts and Ethereum account proofs. It verifies for every $a\in S$:
\[
  \mathsf{VerifyEthAccount}(\sr_0,a,b_0(a),\pi^{\mathsf{acct}}_a)=1.
\]
It then computes salted leaves
\[
  L_a=\Hash(\mathtt{leaf},\kappa_a,b_0(a),\eta_a),
\]
builds the local SMT root $R_0$, computes $B_0=\sum_{a\in S}b_0(a)$ and checks $C_0=\Com(B_0;r_0)$. The program commits $R_0,C_0,n$ and $\sr_0$ as SP1 public values.

\paragraph{Update program.}
The SP1 program \texttt{smt-update} takes public input $(R_{i-1},C_{i-1},R_i,C_i,\Delta_i)$ and private input consisting of compact SMT witnesses, old balances, salts, membership flags and commitment randomness. It checks:
\begin{enumerate}[leftmargin=2em]
  \item $\Delta_i$ is sorted and deduplicated.
  \item Each touched key is either a valid member leaf under $R_{i-1}$ or a valid non-member path.
  \item For member leaves, $b'_j=b_j+\delta_j$ is range-valid and uses the same salt $\eta_j$.
  \item For non-members, the leaf and aggregate remain unchanged.
  \item The compact witness recomputes both $R_{i-1}$ and $R_i$.
  \item $d=\sum_j u_j\delta_j$ and $C_i=C_{i-1}+\Com(d;r_D)$.
\end{enumerate}

\paragraph{Insertion program.}
The SP1 program \texttt{smt-insert} takes public input $(\sr_i,R_i,C_i,R'_i,C'_i)$ and private input containing new addresses, account proofs, balances, salts and old-SMT non-membership witnesses. It verifies Ethereum account proofs under $\sr_i$, checks non-membership in the old local SMT, inserts the salted leaves, and updates the aggregate balance commitment.

\section{Algorithms to Implement}

\subsection{Fast Polynomial Algorithms}

The NIZK route requires the following polynomial algorithms:
\begin{enumerate}[leftmargin=2em]
  \item Product tree construction for $\prod_j(T-x_j)$.
  \item Fast multipoint evaluation of $P_S$ on $x_1,\ldots,x_m$.
  \item Batch inversion for nonzero $y_j^{-1}$ in zero-test witness generation.
  \item Fast interpolation from $(x_j,y_j)$ to $I_y(T)$.
  \item Polynomial division to compute $(P_S-J_Y)/Z_i$.
\end{enumerate}

The benchmark must include a naive baseline that computes all $P_S(x_j)$ independently in $O(nm)$ time.

\subsection{KZG Algorithms}

The KZG implementation supports:
\begin{align*}
  \mathsf{Commit}(f)&=[f(\tau)]_1,\\
  \mathsf{BatchOpen}(P_S,\{x_j\},\{y_j\},\rho_Y)&=(C_Y,\pi_{\mathsf{eval}}),\\
  \mathsf{BatchVerify}(A,C_Y,\pi_{\mathsf{eval}},Z_i)&\in\{0,1\},\\
  \mathsf{BatchVerifyShards}((A_\ell,C_{Y,\ell},\pi_\ell)_\ell,Z_i)&\in\{0,1\}.
\end{align*}
The verifier recomputes $Z_i$, $[Z_i(\tau)]_2$, $H_Y=[Z_i(\tau)]_1$ and rejects if $H_Y=\mathcal O$.
For sharded proofs, $\mathsf{BatchVerifyShards}$ derives randomizers from the transcript and checks one random linear combination of the $t$ KZG equations.

\subsection{SMT Algorithms}

The SMT implementation supports:
\begin{enumerate}[leftmargin=2em]
  \item Salted leaf hashing $L=\Hash(\mathtt{leaf},\kappa,b,\eta)$.
  \item Empty subtree constants for all depths.
  \item Membership proof generation.
  \item Non-membership proof generation: empty path case and collision-leaf case.
  \item Compact multiproof generation for sorted touched keys.
  \item Incremental root update and independent rebuild check.
\end{enumerate}


\subsection{SP1 Programs and Coprocessor Algorithms}

The SMT route implements the following SP1-proved algorithms:
\begin{enumerate}[leftmargin=2em]
  \item \textbf{Initial account-proof verification}: verify all Ethereum MPT account proofs from \texttt{eth\_getProof}, decode account balances, and check consistency with $\sr_0$.
  \item \textbf{Initial local tree construction}: compute salted local SMT leaves and root from the verified balances.
  \item \textbf{Conditional update}: verify compact local SMT proofs, apply only member deltas, and update the aggregate commitment.
  \item \textbf{Insertion}: verify Ethereum account proofs for newly inserted addresses and old-SMT non-membership before inserting salted leaves.
  \item \textbf{Coprocessor batching}: batch Keccak/MPT and SMT hash operations to reduce SP1 cycle count and prover gas.
\end{enumerate}

\subsection{End-to-End Checks}

For every update benchmark, the code should compute a plaintext reference value
\[
  d_{\mathsf{plain}}=\sum_{a_j\in S}\delta_j.
\]
The proof output is accepted only if the privately opened post-update balance satisfies
\[
  B_i=B_{i-1}+d_{\mathsf{plain}}.
\]
For SMT, the new root obtained by incremental update must equal the root obtained by rebuilding the tree from the updated plaintext map.

\section{Implementation Phases}

\begin{enumerate}[leftmargin=2em]
  \item \textbf{Phase 1: data pipeline}. Implement \texttt{eth-sync}, dataset formats, reserve sampling and plaintext correctness checks.
  \item \textbf{Phase 2: NIZK polynomial/KZG layer}. Implement masked set polynomial, fast evaluation, interpolation, quotient and KZG batch verification.
  \item \textbf{Phase 3: NIZK logic layer}. Implement committed-R1CS relation and either full Bulletproof backend or exact constraint/proof-size instrumentation.
  \item \textbf{Phase 3b: NIZK parallel sharding}. Implement shard construction, parallel update workers, batch KZG verification and one aggregate inner-product/projection proof.
  \item \textbf{Phase 4: SMT off-circuit layer}. Implement salted compact SMT, membership/non-membership proofs, compact multiproof and incremental update.
  \item \textbf{Phase 5: SMT SP1 program layer}. Implement SP1 update and insertion circuits with Poseidon hash and range constraints.
  \item \textbf{Phase 6: SP1 initialization benchmarks}. Benchmark Ethereum account-proof verification in SP1, including native execution, mock execution, proof generation and proof verification.
  \item \textbf{Phase 7: benchmarks}. Run synthetic and real Ethereum workloads, export metrics, and generate tables/figures.
\end{enumerate}
